# Soutenance - Questions / Réponses (résumé très détaillé)

Objectif : avoir des réponses précises, structurées et faciles à présenter à l'oral. Chaque question est en gras, chaque réponse est détaillée.

| Question | Réponse |
|---|---|
| **Quel est l'objectif exact du projet ?** | Reproduire les mécanismes essentiels d'une messagerie type WhatsApp : inscription/connexion, recherche d'utilisateurs, demandes d'amis, conversations directes, envoi de messages texte, statut en ligne/hors-ligne. Le but est pédagogique : une stack simple, une architecture claire, et une base fonctionnelle pour une soutenance. |
| **Quelle est l'architecture générale (vision 10 000 pieds) ?** | Application Flutter pour l'UI et la logique client, API PHP pour la logique métier, base PostgreSQL pour le stockage. Le flux est : UI -> `ApiService` -> HTTP JSON -> Router PHP -> Controller -> Service -> Repository -> PostgreSQL. Cette séparation permet de présenter clairement qui fait quoi. |
| **Pourquoi Flutter pour le frontend ?** | Flutter permet un seul code pour mobile (Android/iOS) et web, avec une UI rapide à prototyper. Le projet exploite des widgets standards, une gestion d'état simple (Stateful/Notifier) et un code lisible pour la soutenance. |
| **Pourquoi PHP + PostgreSQL pour le backend ?** | PHP est facile à déployer et à comprendre en soutenance, sans framework pour rester lisible. PostgreSQL apporte un SQL robuste et des fonctions utiles comme `ON CONFLICT` pour les upserts. Le projet force `DB_DRIVER=pgsql`. |
| **Quels sont les fichiers backend les plus importants ?** | `backend/public/index.php` (point d'entrée HTTP + routes), `backend/src/Core/Router.php` (routing), `backend/src/Core/Auth.php` (vérif JWT), `backend/src/Core/Response.php` (format réponse), `backend/src/Service/*` (logique métier), `backend/src/Repository/*` (SQL). |
| **Comment le routing fonctionne-t-il ?** | Les routes sont définies à la main dans `backend/public/index.php`. `Router::add` génère une regex, puis `Router::dispatch` instancie le controller et appelle l'action. Les routes acceptent des variables comme `{id}`. |
| **Quel est le format de réponse API et pourquoi ?** | Toutes les réponses suivent `{ok, data, error}`. Cela simplifie le frontend : un seul format pour détecter succès/erreur, afficher un message utilisateur et gérer les cas 401. Centralisé dans `backend/src/Core/Response.php`. |
| **Comment l'authentification fonctionne-t-elle ?** | À l'inscription : hash du mot de passe (bcrypt). Au login : vérification + génération JWT (`sub`, `iat`, `exp`). Les routes protégées exigent `Authorization: Bearer <token>`. La classe `Auth` décode le JWT et renvoie l'id utilisateur. |
| **Quelle est la durée de vie du token ?** | Le token expire au bout d'1 heure (`exp = time() + 3600` dans `backend/src/Service/AuthService.php`). Côté Flutter, `TokenStorage` vérifie l'expiration et supprime le token si besoin. |
| **Comment le client stocke-t-il l'authentification ?** | Le token JWT est stocké via `flutter_secure_storage` (`frontend/lib/data/storage/stockageToken.dart`). Un cache local évite des lectures répétitives. Si le token est expiré, il est effacé. |
| **C'est quoi l'option "Se souvenir de moi" ?** | Elle sauvegarde le numéro + mot de passe dans un stockage sécurisé (`CredentialsStorage`). Au démarrage, `AuthService.bootstrap()` relit ces infos et pré-remplit l'écran de login. |
| **Comment les numéros de téléphone sont normalisés ?** | Côté backend `Phone::normalize` supprime les caractères non numériques et gère les préfixes FR (`0033`, `33`). Côté frontend `ApiService.normalizePhone` applique la même logique pour éviter les doublons. |
| **Comment marche la recherche d'utilisateurs ?** | L'API `GET /api/users/search` prend `phonePrefix` et `limit`. Le backend exige au moins 2 chiffres et renvoie les users (sauf soi). Le frontend debounce la saisie et affiche les résultats. |
| **Comment fonctionnent les demandes d'amis ?** | `POST /api/friends/requests` crée une demande `PENDING`. On peut `accept`, `decline`, ou `cancel`. La logique est dans `FriendService`. Le frontend affiche un bandeau de demandes entrantes. |
| **Qu'est-ce que l'auto-acceptation ?** | Si A envoie une demande à B alors qu'une demande `PENDING` existe dans l'autre sens, le backend l'accepte automatiquement et crée l'amitié. Cela évite deux demandes croisées inutiles. |
| **Comment l'amitié est stockée en base ?** | Dans `friendships` avec une paire ordonnée (`user_id_a < user_id_b`). Cela évite les doublons et simplifie les requêtes. `FriendRepository::ensureFriendship` applique cette règle. |
| **Comment est construite la liste des conversations ?** | `ConversationService::listForUser` s'appuie sur `MessageRepository::fetchLastMessagesForUser` pour obtenir le dernier message par contact. Ensuite, `ConversationRepository::getUnreadCounts` calcule les non-lus. |
| **Comment sont calculés les messages non lus ?** | La table `conversation_reads` conserve le dernier message lu par utilisateur/contact. Un SQL compare `messages.id` au `last_read_message_id` et compte les messages au-dessus. `markRead` est appelé lors de la lecture. |
| **Comment un message est-il envoyé ?** | Le frontend appelle `POST /api/messages` avec `receiver_id` et `content`. Le backend valide : destinataire != soi, longueur <= 200, amis obligatoires. Puis `MessageRepository::insert` enregistre en DB. |
| **Comment fonctionne la suppression d'un message ?** | Le frontend permet un swipe pour supprimer. `DELETE /api/messages/{id}` est appelé. Le backend vérifie que l'utilisateur est bien l'auteur, puis supprime. |
| **Comment le chat récupère-t-il les messages ?** | `GET /api/messages?with=USER_ID&after=LAST_ID` renvoie tous les messages après un id. Côté Flutter, `_lastMessageId` est mis à jour et les messages sont triés par date. |
| **Pourquoi du polling et à quelle fréquence ?** | C'est la solution la plus simple sans WebSocket. Conversations et messages sont rafraîchis toutes les 1 secondes, demandes d'amis toutes les 2 secondes. C'est efficace pour démo, mais gourmand en réseau. |
| **Comment le statut en ligne/hors-ligne est géré ?** | Le user peut activer "apparaître hors-ligne" via `POST /api/status`. Le chat lit `GET /api/status/{id}`. Si `appear_offline=true`, l'UI affiche "Hors ligne", sinon "En ligne" ou "Vu à" selon `last_seen`. |
| **Pourquoi le "vu à" peut être imparfait ?** | `last_seen` n'est mis à jour qu'au login. Donc si l'utilisateur est actif, l'heure ne se met pas à jour à chaque action. Il faudrait mettre à jour `last_seen` régulièrement ou via middleware. |
| **Comment la logique frontend est-elle organisée ?** | `api/` pour l'HTTP, `domain/` pour l'auth, `presentation/` pour le bootstrap et les controllers, `pages/` pour l'UI, `models/` pour le mapping JSON, `utils/` pour dates/normalisation. |
| **Quels écrans sont critiques à présenter ?** | Connexion/inscription (`authPage.dart`), liste des conversations (`messagerieScreen.dart`), chat (`conversationScreen.dart`), ajout d'amis (`addScreen.dart`), profil/paramètres (`compteScreen.dart`). |
| **Quelles dépendances Flutter sont importantes ?** | `http` pour les appels API, `flutter_secure_storage` pour stocker le token, `flutter_dotenv` pour configurer l'API, `permission_handler` pour demander la notif, `audioplayers`+`vibration` pour feedback. |
| **Comment les erreurs sont gérées côté frontend ?** | `ApiService` normalise toutes les réponses et mappe les erreurs HTTP vers des messages utilisateur. En 401, le token est nettoyé. Les pages affichent snackbar ou dialog selon le contexte. |
| **Quelles limites actuelles faut-il assumer ?** | Pas de temps réel (pas de WebSocket), pas d'upload d'images, pas de groupes, pas de migration SQL, peu de tests automatisés, CORS ouvert à tous. C'est acceptable pour un POC. |
| **Quelles améliorations proposer en soutenance ?** | WebSocket ou SSE pour temps réel, push notifications, support images/fichiers, chiffrement bout-en-bout, migration DB, rate limiting, rôles/permissions, tests unitaires et d'intégration. |
| **Quels sont les risques sécurité/production ?** | CORS `*`, pas de rate limiting, JWT secret en clair dans env, pas de rotation de token, pas d'audit. En prod il faut ajouter validation forte, logs, monitoring et sécuriser les secrets. |
| **Comment lancer le projet en dev ?** | Backend : définir `DB_*` et `JWT_SECRET`, lancer `php -S localhost:8080 -t backend/public`. Frontend : `flutter pub get`, définir `API_BASE_URL` dans `frontend/.env`, puis `flutter run`. |
| **Comment prouver que le schéma SQL est cohérent ?** | Les requêtes SQL des repositories dictent les champs utilisés : `users`, `friend_requests`, `friendships`, `messages`, `conversation_reads`. Le schéma proposé respecte toutes les colonnes accédées. |
| **Pourquoi `conversation_reads` est créé dans le code ?** | Il n'y a pas de migration. Le repository crée la table si elle n'existe pas. C'est une solution rapide pour éviter un script SQL manuel, mais ce n'est pas propre pour un vrai pipeline. |
| **Quel est un point de dette technique majeur ?** | `backend/src/Core/Container.php` instancie `Auth` avec des arguments qui ne correspondent pas au constructeur actuel. C'est un bug potentiel si ce chemin est utilisé. |
| **Comment le client connaît-il l'utilisateur courant ?** | Le `TokenStorage` décode le JWT (champ `sub`). Le frontend l'utilise pour afficher le profil, pour marquer les messages "Moi", et pour certaines décisions UI. |
